# SIRO 優化稽核 + 效能剖析（第一階段）— 2026-10-28

範圍：local main（工作樹含他人未提交修改，未動）。環境：Win11 + WSL2 Ubuntu、GPU 8 GB（約 5.8 GB 被 gemma4:e4b 佔用）、
Ollama 0.34.3、gateway Python 3.14。跳過項目依任務指示（記憶檢索、Rust 移植等）。
量測方式：對 live gateway（:8000）送探針 turn（session `audit-probe`）；另起一個隔離 gateway（:8010，複製 DB、無 TTS/STT，
已關閉並刪除）以 httpx 計時 hook 分離 Python 與 Ollama 時間。數字為單次機器上的實測，會有 ±1 s 的 GPU 競爭波動。

## 一句話結論（給 owner）

**慢的是模型與語音，不是 Python。** 一則文字回覆約 9–12 秒，其中 4–6 秒是 Ollama 在讀「每回合重送的 ~5.9k token 提示詞」，
TTS 合成每句另需 3–6 秒。gateway 閒置 CPU 0.2%、RSS 144 MB。沒有任何量測支持改語言或重寫。

## 1. 效能量測

| 項目 | 實測 |
|---|---|
| gateway 閒置 | CPU 0.2%、RSS 144 MB、啟動到 `/health/ready` ≈ 10 s（含載入） |
| 文字 chat（live，3 回合） | 首個 delta 6.4–7.9 s；整回合 9.0–12.0 s；`affect_state` 事件在 1.5–2.5 s |
| 同路徑（隔離實例，無 TTS/STT 競爭） | 首個 delta 4.3–5.5 s；整回合 4.7–5.9 s；`affect_state` 在 0.05 s |
| 單次 Ollama /api/chat | 請求體 25 KB（system 16 KB）= **5,906 prompt tokens**；冷 prefill 3.3–3.6 s（≈1,800 tok/s）；生成 50–66 tok/s |
| 同提示詞完全重放 | prefill 0.04–0.5 s（前綴快取命中） |
| 空閒 5 分鐘後第一句 | 模型被卸載，**額外 5.6 s 載入**（`load_duration` 5.62 s） |
| TTS（Qwen3-TTS 0.6B，229 次歷史紀錄） | 中位 5.85 s／句，p90 19.4 s，最大 99 s；RTF 中位 0.60。實測 12–33 字 = 3.2–4.0 s；快取命中 0 ms |
| STT（faster-whisper small，CPU int8） | 7 s 語音 → 1.6–2.0 s（RTF ≈ 0.25）；worker RSS 757 MB |
| TTS worker | RSS 2.47 GB（常駐，閒置 CPU 1%） |
| Electron 桌寵（Windows） | main 108 MB、renderer 194 MB、GPU process 105 MB；renderer ≈ 8% 單核、GPU process ≈ 8%，GPU 3D 引擎 ≈ 16%；閒置已降到 20 fps（`renderers/vrm/src/main.js:684`） |
| 工具呼叫 | 本輪未觸發真實工具（避免對 owner 環境產生副作用）；工具耗時由外部 I/O 決定，非 Python |

**時間花在哪（文字回覆，隔離實例）：** Python 前處理 < 0.1 s → Ollama prefill 3.5–5 s → 生成 0.4–1 s。
Live 比隔離實例多約 2 s（`affect_state` 前的等待）與較慢的 prefill，最可能原因是 GPU 與 TTS／背景 foreground 作業競爭
（`create_turn` 會 `await goal_owner/self_activity/memory_organizer.foreground()`）——假設，未逐一隔離驗證。

   **大改，僅提案**。另一方向：Gemma 的 prefix cache 只在整段前綴相同時才有大幅命中，把會變的段（時間、source context、dialogue projection）
   後移的初步實驗**未見改善**（3.3 s 不變），故不建議只靠重排。
2. **依賴漏洞（pip-audit，51 筆 / 4 套件）** — aiohttp 3.14.3→3.14.4（8 筆）、certifi 2026.7.22→2026.10.19、filelock 4.0.11→4.2.1、

## 4. 漏洞檢查結果

- **Gateway 綁定／CORS／驗證**：僅綁 `127.0.0.1`（`config.py:66` 限定 loopback；`gateway.py:3106`）。HTTP 無 CORS 中介層，所有 `/v1/*` 需
  Bearer session token；token 由 `POST /v1/session` 發出，需 `Origin` 在白名單且 `client.host` 為 loopback；WS 檢 Origin 並要求 3 s 內 `authenticate`；
  token TTL 300 s、上限 128 枚、`secrets.token_urlsafe(32)`；ESP32 relay token 用 `compare_digest` 且 ≥32 字元。**設計良好。**
  殘留風險（可接受、記錄即可）：本機任一行程可偽造 `Origin` 自取 token（loopback 信任模型）。
- **子行程／shell 注入**：src 內**無** `shell=True`、`os.system`、`eval/exec`、`pickle`、`yaml.load`、`extractall`；所有子行程皆
  `create_subprocess_exec` argv 陣列；`ProcessDriver._validate_command` 檢查 NUL 與 cwd 在允許根內（argv 本身不做白名單，防線在
  orchestrator 的核准流程；`authorization_mode` 預設 `"full"`，建議確認 UI 實際要求逐次核准）。bandit -ll：0 High、13 Medium，
  皆為 B608（SQL 以 `?` 佔位符串接固定片段，非使用者輸入；已抽查 `persistence/memory.py:491/514`）、B108（`/tmp`）、B310（urlopen 固定 loopback URL）。
- **路徑穿越**：未發現直接可利用路徑；`filesystem.*` 工具與 workspace 走 scoped runtime（未逐行審計，列入下一階段）。
- **Secret 洩漏**：repo 追蹤檔與 git 全歷史（326 commits）搜尋 Wi-Fi／SSID／PSK／password／token 字面值：
  **Wi-Fi 密碼不在 repo 中**（firmware 僅 `secrets.example.h` 的 `replace-me`，`secrets.h` 在 `.gitignore`，歷史中從未提交）。
  `.env` 系列已忽略，僅追蹤 `.env.example`。live `siro.log`（含歷史）未出現 bearer／api key。`~/.config/siro/*` 權限 600／700。
  repo 內有 `scripts/check_secrets.py` 閘門。
- **依賴漏洞**：見 P1-2。

## 5. 其他讓 SIRO 更好的提案

- 在 gateway 加每回合分段計時日誌（preface／prefill／first token／TTS queue），之後優化不用再臨時掛 hook（我用的 hook 在 scratchpad，未入庫）。
- TTS 與 LLM 同在 8 GB GPU 上競爭；若 prefill 的波動是 owner 實際感受的主因，可考慮 TTS 走 CPU 或限制並行（需 A/B 量測）。
- 對話提示詞預算：`SIRO_CONTEXT_TOKEN_BUDGET_ENABLED=0` 目前關閉；若啟用並把 system 控在 ~3k token，估計首字再省 1.5–2 s（需評測品質）。
