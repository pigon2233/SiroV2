## Smallest proposed repair contract

1. Keep `async restore_from(source: Path) -> None` and the same per-instance writer lock. Do all blocking SQLite/file work off the event loop within one owned operation.
2. Open the selected source read-only (`mode=ro`, plus query-only); a missing source must not create an empty database. Use a SQLite backup snapshot into an owned temporary candidate rather than raw main-file copying. Do not use `immutable=1` as a shortcut that could omit committed WAL contents.
3. Validate candidate integrity and a known contiguous migration prefix. Exact bundled version/name/checksum identity is required for applied entries; unknown/future/gapped or conflicting metadata fails before opening/mutating live. Preserve the original supported v0/older-backup migration behavior as explicitly exercised by tests. Keep this guard local to restore; do not alter existing SQL migrations or the general migration engine merely for this card.
4. Apply the existing bundled migrations to the candidate only. Check final candidate integrity. Any source/metadata/migration failure must preserve original typed failure and leave live rows, ledger and stable-fixture live/WAL bytes untouched.
5. Only after candidate validation/migration passes may promotion begin. Use SQLite backup candidate→existing live connection, preserving target inode/WAL/connection identity. Do not `os.replace` a live database file or silently restore a second snapshot after an unknown copy failure.
6. Single/repeated caller cancellation must keep the operation owned and writer lock held until the off-loop worker and cleanup have been joined. Cancellation during preparation should fence promotion with a thread-safe stop state checked immediately before the live boundary. Once live backup has begun, join and report the actual cancelled/unknown outcome; do not claim that cancellation rolled back a completed effect or automatically retry it.
7. Explicitly close source/candidate/target connections. A `sqlite3.Connection` context manager commits/rolls back but does not itself close the connection. Candidate cleanup occurs after those closes and joins. Remove only this operation's candidate and its owned SQLite sidecars; cleanup must not mask a primary `MigrationError`/SQLite failure. A cleanup failure after otherwise successful work must not be reported as an uncomplicated success.

Source==live is **not** a confirmed new policy defect. The repair's candidate snapshot can preserve this existing caller behavior; root explicitly chose a same-file positive compatibility test instead of adding an unproved source/alias rejection policy. This review does not require new path authorization or a generalized filesystem security layer.

## Risks that should not expand this card

- A final-copy failure must have an observed outcome and must not trigger a hidden automatic restore/retry. Power-loss durability, arbitrary concurrent external writers and live production maintenance are not established by temporary fixtures.
